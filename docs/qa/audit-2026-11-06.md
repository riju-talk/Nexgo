## 2. Findings

Severity: **High** blocks revenue or trust, **Med** wrong or confusing behaviour, **Low** polish.

### A. Booking and couriers
- **A1 (High, V)** The create-order courier list offers couriers that cannot take the parcel. The cheapest option (Amazon Surface 0.25 kg) is pre-selected; **Book selected courier** returned **422** on every attempt. The same order booked fine through auto-assign (Shadowfax). Quotes come from NEXGO rate cards only; Lorrigo's serviceability is checked only at booking time. The rejection reason was not visible to the tester (toast disappeared before it could be read) — the failure feedback needs to be persistent.
- **A2 (Med, V)** Two flows disagree: the create-order page pre-selects the cheapest courier, while the Ready-to-ship "Book now" chooser deliberately selects nothing (client request).
- **A3 (Med, C)** Booking reads only the newest active rate card per seller. Saving rates in Admin creates a new card each time and never retires the old ones (seller `xpresszone` has two active cards). Harmless today, but any flow that saves a partial card silently drops couriers.

### B. Onboarding and account state
- **B1 (High, C -> fixed locally, not deployed)** While the agreement is not accepted, the gate replaces every page, including the dashboard, so live analytics never render. Local fix: agreement and KYC cards sit on top of the page, nothing is hidden; full-width welcome card. Needs deploy.
- **B2 (High, C)** Production data: of 7 sellers, 4 have not accepted the agreement (`ATYA INNOVATION`, `himizone`, `coverhub`, `Starship` before today) — they can still not create orders. One seller (`XpressZone`, duplicate of `xpresszone`) has no courier access and no rate card.
- **B3 (High, C)** Wallets: `xpresszone` has ₹0 and 50 orders in Ready to ship; every assign fails on balance. `coverhub`, `Starship`, `ATYA INNOVATION` also ₹0.
- **B4 (Med, V)** A new seller cannot do anything useful until an admin assigns couriers, a rate card and wallet money, and the seller adds a warehouse. The app gives no checklist for these (the only checklist is the KYC bar).
- **B5 (Med, V)** Create-order form: Dead weight shows a grey suggestion (0.400) but is empty, so the browser blocks submit with "Please fill in this field". The suggestion looks like a value.

### C. Money and ledger
- **C1 (Low, V)** Wallet transactions: the cancellation-refund row shows the shipment UUID in "Ref No" instead of the AWB.
- **C2 (Med, C)** RTO freight is now billed going forward, but earlier RTO shipments were never billed and are not back-filled (finance decision).
- **C3 (Low, V)** Under 48 parallel requests the API takes 1.5-2.3 s per call (DB pool maximum 12). Not a normal load, but worth a pool/index look before volume.

### D. Tracking, notifications, integrations (carried over)
- **D1 (High, C)** Tracking arrives only by Lorrigo webhook (no polling fallback). Whether the webhook URL and `LORRIGO_WEBHOOK_TOKEN` are configured on RDS/EC2 is unverified (query 6 was not run).
- **D2 (Med, C)** No customer notifications (WhatsApp / SMS / e-mail) — no provider connected.
- **D3 (Med, C)** Settings -> Webhook is a mock screen: no outbound webhook dispatcher.
- **D4 (Med, C)** Shopify: only the first fulfilment is pushed; delivered / RTO are not pushed back. Order sync for the other channels is a placeholder. Never tried against a real store.
- **D5 (Low, C)** Pickup scheduling is a database record only (Lorrigo offers no API).

### E. Security and hygiene
- **E1 (Med)** The tester's password was pasted into the chat during this session. Rotate it.
- **E2 (Low)** `.env` (dev) now points at the RDS URL, which is unreachable from developer laptops; local dev needs a separate env file.
- **E3 (Low)** Test data left in production: warehouse "Test Warehouse Mumbai", cancelled order `WEB-982395` / cancelled shipment `SF4426876336DFO`, wallet credit note `CN-TEST-261106` (+₹6,000), seller "Starship" owner `rijusmit.biswas@gmail.com`.
